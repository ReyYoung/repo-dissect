# 分层拆解细则

> 本文件是 repo-dissect 的参考资料。做到哪一层，读对应小节即可，不必一次读完。证据标记 ✅ 🔍 ❓、永久链接格式、安全规则见 SKILL.md 第 5 节；出图见 `charts-and-report.md`。

## 目录

按标题查找：L0 项目画像 · L1 业务全景与功能架构 · L2 技术架构 · L3 主流程追踪 · L4 核心模块精读 · L5 复用评估 · R 选型评估 · Q 需求响应矩阵 · 对比模式 · 可借鉴设计 · 常见误判清单

## L0｜项目画像 → `00-画像.md`

读 README、顶层目录、依赖清单（package.json / pyproject.toml / go.mod / Cargo.toml / pom.xml 等）、LICENSE、CHANGELOG、`git log --oneline -30`。先运行 `. "$OUT/_vars.sh" && python3 "$SKILL_DIR/scripts/repo_stats.py" "$SRC" --json "$OUT/_stats.json"`（`$SRC` 是源码目录：取码时为 `$OUT/src`，本地仓库为用户给的路径）：文件数、各语言行数、近一年提交数、作者占比、测试和 CI 的数字都从它取，连同它给出的口径一起写，不要自己另用命令重算（不同的算法会得出不同的数字）。产出：

1. **一句话定位**：解决什么问题、给谁用；并判断**项目类型**——应用型产品（有界面、面向最终用户）/ 库或 SDK / 框架 / 命令行工具 / 基础设施或中间件。类型决定 L1 怎么做
2. 技术栈和关键依赖，标出重型或少见依赖；列出运行需要的外部服务（数据库、消息队列、向量库、模型 API 等）
3. 顶层目录职责表（Monorepo 则列各包）
4. License 初判：根目录协议类型；是否有附加条款或单独授权的目录；随仓库带的第三方组件或外部工具（`licenses/`、`third_party/`、`NOTICE`）按"组件 | 协议（以原文为准）| 怎么用"单列，不把组件协议写成整个工具的协议（深查见 R 层）。只做与目标相称的初判：架构学习只需知道边界，不因发现 MPL、GPL 组件就判"不能用"
5. 入口在哪里（CLI / Server / 库的导出 / 前端入口）
6. 活跃度与社区：
   - 社区数据走 REST 接口：`gh api repos/<owner>/<repo>`、`gh api 'repos/<owner>/<repo>/releases?per_page=10'`（`gh repo view`、`gh release list` 走 GraphQL，在部分环境不可用）；`gh` 不可用时用任何能读网页的方式（HTTP 工具或 `curl -s`）读 `https://api.github.com/repos/<owner>/<repo>`。记录 star、fork、未关闭 issue、发版节奏，注明采集日期；`open_issues_count` 包含未合并的 PR，要么写"未关闭 issue + PR"，要么用 `gh api 'search/issues?q=repo:<owner>/<repo>+type:issue+state:open'` 单独取 issue 数
   - API 数据可能是缓存，时间类数据（最近推送、发版日期）以本地 `git log`、`git tag` 为准，二者矛盾时写明
   - 维护者集中度：用 `repo_stats.py` 的作者占比。分母是统计窗口内的**全部**提交，不是前几名之和；疑似别名在核实前不合并（要合并就写明合并了谁、依据是什么）。前 1–2 人提交占比超过约 70% 标为维护者风险，写的时候带上窗口和分母，例如"HEAD 往前 365 天共 5,515 次提交，首位占 61.7%"。没有 `repo_stats.py` 可用时退回 `git shortlog -sn --since=1.year HEAD`（必须带 `HEAD`，否则非交互环境会卡住等待输入），分母用 `git rev-list --count --since=1.year HEAD`
7. **结论：是否值得深挖，理由用 3 条以内说明**

**闸门**：L0 完成后向用户汇报第 7 条，确认后再继续。对比模式下等所有仓库的 L0 都完成后统一汇报一次。大仓库要在 L2 之后选题时，这一步并进选题那次一起汇报，不单独停（见 SKILL.md 第 0 节）。用户已要求全流程或无人值守时跳过，并在 `index.md` 记一笔；跳过闸门不等于委托选题。

## L1｜业务全景与功能架构 → `01-业务全景.md`

站在产品经理和售前的视角回答：它能干什么、给谁用、业务怎么跑。同样以代码为证，不照抄 README 的宣传语。

**按项目类型调整**：

- **应用型产品**：完整做下面全部产出项。
- **库、SDK、框架**：功能清单改为"对外能力清单"（来自公开导出的类、函数、配置项）；使用场景从 `examples/`、文档示例和测试中提取；第 4 条改为核心数据结构关系；跳过第 6 条角色与权限。
- **命令行工具**：功能清单按子命令和主要参数组织；跳过第 4、6 条。
- **基础设施或中间件**：功能清单按能力和协议接口组织；第 5 条改为数据或请求的处理流程；第 6 条改为认证与访问控制方式。

**取证来源**（按可靠程度排序）：

| 来源 | 能提取什么 | 常见位置 |
|---|---|---|
| 前端路由和菜单配置 | 功能清单、页面层级 | `router/`、`routes.*`、`menu*`、`sidebar*`、Next.js 的 `app/` 或 `pages/` 目录 |
| i18n 语言包 | 功能名、页面名、按钮文案，通常最全 | `locales/`、`i18n/`、`zh-CN.*`、`en.*` |
| API 路由 / OpenAPI 定义 | 对外能力清单 | `openapi.*`、`swagger.*`、controller / router 文件 |
| 数据模型 | 业务对象及关系 | ORM model、`migrations/`、`schema.sql`、`schema.prisma` |
| 枚举和状态字段 | 业务状态流转 | `enum`、`status`、`type`、`*_STATE` 常量 |
| 权限定义 | 角色和权限粒度 | `role`、`permission`、`rbac`、`policy`、`casbin` |
| 系统设置页和配置项 | 可配置、可运营的能力 | settings 页面、`.env.example`、配置 schema |
| 运行截图（SKILL.md 第 3 节） | 功能是否真实存在于界面 | `img/screens/` |
| 官方文档站、Demo | 补充说明 | `docs/`、官网（只能作 🔍 推断，不算代码事实） |

**产出**：

1. **业务全景**：
   - 目标用户与角色：区分终端用户、管理员、开发者/运维
   - 3–6 个核心使用场景
   - 价值主张：为什么用它而不用别的
   - 一张**业务全景图**，用「场景走廊图」模板出图（见 `charts-and-report.md`，不用 Mermaid）：每行一个场景，依次是角色、场景名与一句话说明、依赖的系统能力、连接的外部系统
2. **功能架构图**：用「分层方块图」模板出图（见 `charts-and-report.md`，不用 Mermaid），按解决方案常用的分层组织，例如：用户入口 → 应用功能 → 平台能力 → 数据存储 → 基础设施。层与层之间不画箭头；核心能力标 `focus`；企业版能力单独成一个虚线分组；实验性、仅某后端可用的用状态标签。
3. **功能清单表**：`一级模块 | 二级功能 | 说明 | 入口（页面/API/截图） | 出处 | 版本归属 | 成熟度`
   - 版本归属：社区版 / 企业版 / 云服务专属。线索有 `ee/` 目录、License 校验代码、feature flag、`isEnterprise` 一类的判断
   - 成熟度：稳定 / 实验性（beta、feature flag 关闭）/ 只有后端没有界面 / 只有界面占位未实现。写"稳定"要有来源（官方文档或发布说明的定位、测试覆盖、运行截图），没有来源时写"未评级"（不要用"未见实验标记"代替成熟度结论）；"本次是否验证过"（截图、运行）在"入口"列或单独一列说明，不和成熟度混在一起
   - 版本归属要顺着链路查：界面入口 → 调用的接口 → 接口是本地实现，还是转发给商业版服务 / 只在商业版里注册。只有枚举、菜单、开关、语言包里的文案，不能说明社区版可用
   - 一级模块全部列出；正文的二级功能控制在约 60 行以内，按重要程度取舍，其余放到文末 `## 附录：完整功能清单` 小节（报告页会自动折叠）
   - **对照发布说明**：读 CHANGELOG / release notes 中的废弃（deprecated、removed）说明，已废弃的功能即使代码还在，成熟度也要标"已废弃"
4. **核心业务对象**：Mermaid `erDiagram`，只画 8–12 个核心实体及关系。实体名用代码里的英文模型名（中文实体名在部分 Mermaid 版本中渲染易出错），图下附一张"实体 | 中文含义 | 模型定义出处"表
5. **关键业务流程**：从用户视角写 1–3 个端到端流程（Mermaid `flowchart`）；核心对象有状态字段时，用 `stateDiagram-v2` 画状态流转
6. **角色与权限模型**：有哪些角色；权限细到哪一级（菜单 / 按钮 / 数据行）；多租户或工作空间怎么隔离
7. **集成与开放能力**：对外 API、Webhook、SSO / LDAP / OAuth、插件或扩展机制、数据导入导出
8. **业务差距**（提供了使用场景才做；有需求清单时以 Q 层为准，这里只写清单之外的明显缺口）：对照用户的行业和场景，列出缺失或薄弱的能力，例如审批流、审计日志、细粒度权限、国产化适配、报表，并估计补齐难度（S/M/L）

L3 主流程追踪的场景，从这里第 1 条的核心场景中挑选。

## L2｜技术架构 → `02-技术架构.md`

以代码为准，不以 README 为准：

1. 模块划分和分层，用 Mermaid `graph` 画模块依赖图（节点不超过 15 个，太多先聚合）
2. 核心抽象（关键类、接口、数据结构），每个附出处
3. 模块间通信方式：直接调用、事件、队列、HTTP 或 RPC
4. 配置从哪里加载，状态和数据存在哪里
5. 部署形态：单体还是多服务，从 docker-compose / Helm / K8s 清单看有哪些组件
6. 功能到模块的映射：L1 功能架构图里的每个功能模块，分别由哪些代码模块实现（一张对照表）
7. **四类边界分开写**，不要用一个"全部 / 唯一"概括：
   - 配置从哪来：环境变量、配置文件（包括环境变量指向的文件）、命令行或接口参数、写到其他客户端的配置，分别由谁读写；
   - 资源归谁管：自己启动并负责清理的进程、挂接到已有的会话或程序、只连接外部服务，三者的控制权不同；
   - 有没有队列：独立部署的消息服务（Kafka、Redis 队列等），和进程内的排队（内存 FIFO、任务队列类）是两回事；
   - 资源怎么释放：显式清空（close、clear）、按策略淘汰（LRU、过期）、依赖 GC，以及"长时间运行会不会累积"
8. **机制候选表**（文件最后一节，标题用「机制候选」）：列出 5–8 个这个项目里最值得精读的机制，作为 L3 选主流程、L4 选模块的依据：

   | 机制 | 位置（代码引用） | 为什么独特 | 路径变体 | 与目标的相关度 | 证据可得性 |
   |---|---|---|---|---|---|

   - **为什么独特**：和同类项目的常见做法比，它不一样在哪（如"查询时才合并身份，不改写历史数据"），说不出差异的不进表；
   - **路径变体**：同一个机制有几条执行路径，默认走哪条、按什么切换。常见的有：默认实现和旧版兼容实现（如原生函数调用和旧的提示词式调用）、按部署变体切换（精简镜像和完整镜像）、按后端切换（数据库原生检索和客户端检索）、有会话和无会话两种返回方式。只有一条就写"单一路径"。L3、L4 写结论时要标明说的是哪条路径；
   - **与目标的相关度**：高 / 中 / 低，按第 0 节的主目标和使用场景判断；
   - **证据可得性**：代码是否完整、有没有测试或注释、能否在本次运行里验证；
   - 不按文件热度或提问的字面意思选：热点文件、用户问到的模块都可以进表，但要和其他候选一起排序；
   - L2 是按概述深度写的，可以粗一些；L3、L4 取证后发现 L2 的说法不对（例如机制其实在别的目录、"全部 fail-closed"其实分情况），**回到 L2 改正**，并在对应的 L4 里写一句"与 L2 原说法不一致之处"。

## L3｜主流程追踪 → `03-主流程.md`（技术上最关键的一层）

**选场景**：从 L1 的核心场景里挑一条能串起 L2「机制候选」表中排名靠前机制的路径；其次参考 README 快速上手、`examples/`、端到端测试覆盖的路径。写明为什么选它、它经过了候选表里的哪几个机制。

从入口一路追到结果返回：

- 调用链表格：`步骤 | 出处 | 函数 | 做了什么 | 传给下一步的数据`
- 用 Mermaid `sequenceDiagram` 画时序图。一张图只讲一个阶段（≤ 6 个参与者、≤ 12 条消息），完整流程按阶段拆成几张（例如"打开与选择 / 处理与记录 / 导出与关闭"）；只负责转交的中间层写进图注，不占泳道。失败分支画到终止为止，不接回成功主线；不同平台行为不同的步骤分开画或在图注说明
- 每一步写实际发生了什么：区分"创建对象"和"真正启动进程 / 发起连接"（懒加载要写清在哪一步才触发）、"返回确认信息"和"返回正文内容"
- **路径变体分开写**：链路经过 L2 候选表里有多条路径的机制时，写明这条链路走的是哪条（默认值是什么、靠哪个配置或参数切换）；另一条路径行为不同的步骤单独列出，不把一条路径上的顺序或返回方式推广到所有请求。决定走哪条路的条件有几个就写几个（例如"后台任务看会话 ID 和对话 ID，事件回写只看对话 ID 和消息 ID"），不合并成一个
- 标出关键分支、异常处理、并发或异步边界
- 运行验证按 SKILL.md 第 3 节执行：跑相关测试或最小示例，必要时在副本里临时加日志，写明验证方式、结果和验证级别（V1–V4）；只做了静态阅读（V0）时不在章节里重复写，统一放首屏提示条和报告说明
- L4 精读时如果修正了这条链路上的某一步，回到 L3 同步改正文和图

## L4｜核心模块精读 → `04-核心模块-<模块名>.md`

**选模块**：从 L2「机制候选」表里挑；小仓库 1–3 个，超过规模阈值的大仓库 1–2 个，并且**由用户选**（用户选得更多时，按 SKILL.md 第 0 节"用户选的超过上限"分方向执行）（推荐不等于选择，规则见 SKILL.md 第 0 节"需要用户拿主意的地方"）。按"与目标的相关度 → 为什么独特 → 证据可得性"排序，在文档开头用一两句写明选它的理由。

- **请用户选时**：把候选表的前几行连同"为什么独特"一起给用户，不只给模块名；用户选定后，告诉用户这样会**排除哪些关键机制**（例如"选了聊天助手，就不会精读自动调查引擎，二者是两条不同的链路"），让用户知道选择的代价。
- **每份 L4 文档的开头**：列出候选表里这次没有精读的关键机制，以及不精读对结论的影响（一两行即可）。一份 L4 只覆盖一个方向时，列**本方向内**没精读的机制，整体覆盖范围写在 `index.md`。
- **文件名**用 `04-核心模块-<模块名>.md`：报告生成、章节排序等都按 `04-` 识别精读文档；`checklinks.py` 遇到 `04_`、`4-` 这类变体也会检查六块，但会报错要求改名。"没精读的关键机制"这一节不算六块中的任何一块。

每个模块写一份，**必须包含下面六块，各用一个小标题**（`checklinks.py` 会检查 04- 开头的文档，小标题里要出现对应关键词，缺了报错）：

1. **解决的问题与输入输出**：它解决什么问题；输入什么、输出什么、谁调用它
2. **核心机制（算法或不变量）**：关键算法、数据结构或它始终保证的不变量，配精简代码片段（标注出处）。写"A 由 B 派生 / 决定"时，核对实际函数的输入和返回：两样东西只是在同一个地方组装，不等于一个派生自另一个。按**注册 → 选择 → 执行 → 结果 → 释放**把机制追一遍（不适用的环节写"无"），每一环引用调用点；有多条路径变体时，每条结论标明属于哪条路径
3. **失败边界**：什么情况下会出错、降级或给出错误结果；有哪些限制；最好给一个能验证的反例或边界条件
4. **设计取舍（替代方案与证据）**：可选的其他做法，作者为什么选了现在这个；每条取舍注明证据等级（✅ 有 commit / PR / 注释佐证，🔍 从代码推断）。找证据：`git log --follow -p -- <file>`、`git blame -L <a>,<b> <file>` 定位引入该设计的 commit，再看 commit 信息、关联 PR/issue（`gh pr view`）和注释；源码包没有 git 历史时，用 `gh api "repos/<owner>/<repo>/commits?path=<file>&per_page=20"` 查这个文件的提交记录
5. **适用条件与可借鉴之处**：这个设计在什么条件下成立、换个场景还成不成立；哪些模式值得借鉴。建议的做法如果比原设计弱（放松校验、改变失败策略、去掉所有权检查），明确写"这是另一种设计"，列出它新增的前提和没被证明的地方，不能说成原设计的自然延伸
6. **技术债**：已知问题、TODO、绕过的写法、测试缺口

验收看内容是否到位，不按字数或链接数量：六块都写了、核心机制有代码出处、失败边界至少一条具体情形、设计取舍写了替代方案。

目标是**架构学习或写教程**时，每份 L4 在开头（"没精读的机制"之后）再加一段**阅读路线**：3–6 步，例如"入口 → 主函数 → 状态和数据模型 → 失败路径 → 测试断言"，每步写读哪个函数、读完要能回答什么问题；附一个输入输出例子（没实际运行过的标"按源码构造，未运行"）和一个反例（例如"注册成功但引擎不可用"），帮读者看清这个模式的边界。

## L5｜复用评估 → `05-复用评估.md`

围绕用户的具体目标：

1. 最小依赖集：需要哪些文件，依赖链有多长
2. 扩展点：插件、钩子、接口、配置项
3. 改动量估算（S/M/L）和主要风险：每个 S/M/L 写清边界（例如"加一个只读节点是 S；涉及权限、数据迁移或计费的节点要重估"），不一刀切
4. 复用方式对比：直接依赖 / fork 修改 / 包装调用 / 只参考思路。**推荐写成条件分支**——"如果客户需要 X → 选 Y，代价是 Z"，不要把某一条路线写成所有场景的答案；客户需求还不清楚时，写出决定选哪条路的 2–3 个关键问题
5. License 对这种复用方式的影响（按 R 层第 2 条清单深查）
6. "能不能抽出来"要分清：原样拿走 / 加适配层解耦 / 重构后抽取 / 只借鉴思路。依赖多、耦合深说明成本高，不等于技术上不可行
7. **国产化适配检查**（使用场景里有信创、国产化约束时做；没有就跳过，不写空表）：数据库、中间件、模型接口能不能换成国产组件，换的代价多大。按组件逐行列表：

   | 组件类别 | 项目现在用的（证据） | 接入方式 | 国产候选 | 替换代价 | 主要障碍 / 改动点 |
   |---|---|---|---|---|---|

   - **范围**：
     - 数据库：关系库、向量库、搜索引擎、缓存、图库；
     - 中间件：消息队列、对象存储、Web 服务器和网关、任务调度；
     - 模型接口：大模型、Embedding、Rerank、OCR / 语音。

     国产 CPU、操作系统、ARM 镜像属于运行环境，在 R 层第 5 条查，这里不重复。
   - **接入方式决定代价，先查它**：
     - 走 ORM / 方言层 / 统一客户端（SQLAlchemy、Peewee、Prisma、GORM、MyBatis、LangChain / LiteLLM 一类的模型抽象）还是直连；
     - 有没有方言专属写法：原生 SQL、存储过程、扩展（`pgvector`、全文检索、JSONB 操作符、`ON DUPLICATE KEY`）、厂商专有 API；
     - 模型接口能不能配置 `base_url` 走 OpenAI 兼容协议；模型名、tokenizer、函数调用格式、Embedding 维度是不是写死在代码里。换 Embedding 模型通常要重建索引，算进代价。

     搜索时中英文、拼音一起搜（见 SKILL.md 第 2 节），每类数一数出处，写明搜了哪些目录、用了什么关键词。
   - **代价按 S/M/L 写边界**：
     - S：只改配置或连接串；
     - M：要加适配层，或改写少量方言 SQL / 调用点（写出大概几处）；
     - L：核心逻辑依赖某个组件的专有能力（例如向量检索、全文检索、事务语义），要重写或换架构。

     数据迁移、存量数据转换单独写一行，不藏在"改配置"里。
   - **"兼容"不等于"能换"**：国产库宣称兼容 MySQL / PostgreSQL / Redis / S3 协议时，把项目实际用到的特性逐项列出来核对；没有实际运行过的写"按文档推断，未验证"，验证级别按 SKILL.md 第 3 节标。不写"可以直接替换"，除非在目标组件上跑通过。
   - **国产候选**：用户或客户指定了产品就按指定的查；没指定时，每类列 1–2 个常见选项作为方向（例如关系库从达梦、人大金仓、openGauss、OceanBase 里选，大模型从 DeepSeek、通义千问、GLM 的私有化部署里选），并标"未核对兼容性"。
   - **结论**：
     - 写整体能不能做、总代价（S/M/L 的组合）、最大的一两个障碍；
     - 写交付前需要客户确认的问题（目标产品和版本、是否接受兼容模式、存量数据量）。

     结论放进 `index.md` 的「关键结论核对表」。

## R｜选型评估 → `06-选型评估.md`

1. **功能匹配度**：引用 L1 的功能清单和业务差距（有需求清单时引用 Q 层统计），说明对用户场景覆盖了多少、缺什么
2. **License 深查**：
   - 读完根 LICENSE 全文，不只看名字。特别注意"Apache 2.0 + 附加条件"这类改版协议（例如限制多租户 SaaS、禁止移除 Logo 和版权信息）
   - 识别非 OSI 开源的 source-available 协议：BSL、SSPL、Elastic License、Sustainable Use License、Commons Clause
   - **协议分类以原文为准**：MPL、EPL、LGPL 是文件级或库级的弱 copyleft，CC-BY 要求署名，都不是"无要求的宽松型"；查不到协议的标"未知"，不默认算宽松。顶层协议和组件协议分开记（例如一个工具顶层是 Apache-2.0，附带了 GPL 组件的声明，不能写成"它是 GPL"）；对使用场景的影响单独分析，不从类别直接推"合法 / 违法"
   - 查子目录单独授权：`git ls-files | grep -iE 'licen[cs]e|copying|notice'`，留意 `ee/`、`enterprise/`、`premium/` 目录
   - 依赖协议：有工具就用（`npx license-checker --summary`、`pip-licenses`、`go-licenses`），否则抽查重型依赖；标出 GPL / AGPL / LGPL
   - **写明扫描口径**，否则"未发现 GPL"会被读成"整个交付物合规"：扫了哪些生态（npm / Python / Go / Rust…）；依据是锁文件里的确切版本、registry 元数据，还是包内 LICENSE 文件；共多少个包、多少个查不到或失败；没覆盖什么（镜像里的系统组件、前端打包进去的第三方资源、模型文件）。"未发现"后面总要带上范围
   - 对照使用场景（内部使用 / 私有化交付 / SaaS 多租户 / 二次销售）逐条写：能否、条件、风险
3. **健康度**：最近提交、发版节奏、未关闭 issue 数、抽样近期 20 个 issue 看首次回复时间、维护者集中度、测试和 CI（数字和口径用 `repo_stats.py` 的结果）、文档质量、Release notes / CHANGELOG 中 breaking change 的频率
4. **安全**：`gh api repos/<owner>/<repo>/security-advisories` 查已公开漏洞（无 `gh` 时读 `https://api.github.com/repos/<owner>/<repo>/security-advisories`）；有条件就跑依赖漏洞扫描（`npm audit`、`pip-audit`、`osv-scanner`）；看密钥和权限的处理方式
5. **部署与运维成本**：组件数量、资源需求、升级和数据迁移方式；场景约束检查（用户给了才做）：如信创/国产化——有无 ARM 镜像、能否在国产 CPU 和操作系统上运行，数据库、中间件、模型接口能否换成国产组件；中文支持；能否内网离线部署。组件替换按 L5 第 7 条的表逐项写代价；这次不做 L5 时，把那张表写进 `06-选型评估.md`
6. **替代方案**：至少列 2 个同类项目（awesome 列表、GitHub topics、Web 搜索），各用一句话说明差异
7. **结论**：推荐 / 有条件推荐（写明条件）/ 不推荐，主要理由不超过 3 条

## Q｜需求响应矩阵 → `07-需求响应矩阵.md`（提供了需求清单才做）

1. **整理需求条目**：读取需求清单，拆成可逐条判断的原子需求。保留原文编号和原文表述；原文没有编号就按"章节-序号"编号。一条原文包含多个要求时拆成子条目（如 3.2-a、3.2-b）。非功能需求（性能、安全、部署环境、信创、等保等）单独成组。
2. **逐条响应**：`需求编号 | 需求原文（摘要） | 响应结论 | 对应功能（L1） | 证据 | 差距说明 | 二开工作量`
   - 响应结论五档：**满足** / **部分满足** / **需二次开发** / **仅企业版满足** / **不满足**
   - 判"满足"必须有代码证据或运行截图；只在文档里看到的最多判"部分满足"并标 🔍；拿不准的标 ❓ 并写明需要怎么验证，不硬判满足
   - "需二次开发"要写清楚改哪里（引用 L2 / L5 的模块和扩展点）和工作量估计（S/M/L）
   - 性能类需求（并发数、响应时间、数据量）通常无法从代码确认，标 ❓ 并建议压测方法
3. **统计与结论**：各档条数和占比；关键差距 Top 5；整体判断（能否作为底座、主要补齐工作）。
4. **多项目对比时**：矩阵每个项目一列，便于横向比较。
5. 用户需要填回原表或交给客户时，另外生成一份 Excel 版矩阵（如用 Python `openpyxl`；环境里装不了就输出 UTF-8 BOM 编码的 CSV，Excel 可直接打开）。

## 对比模式 → `compare.md`

每个仓库各自产出 L0、L1、L2、R（精简版）后，输出两张表：

1. **功能覆盖矩阵**：行是功能点（合并各项目 L1 的功能清单，按一级模块分组），列是项目，单元格填 ✅ 有 / ◐ 部分或实验性 / 💰 企业版 / ❌ 无，每个 ✅ 可追溯到对应项目的功能清单出处
2. **综合对比表**：定位、目标用户、技术栈、架构形态、扩展性、健康度、License（按使用场景）、部署成本、主要风险、结论

最后给出选择条件："如果……选 A；如果……选 B"。

## 可选 → `99-可借鉴设计.md`

把可以跨项目复用的设计提炼成卡片，每张包含：模式名、出处、适用场景、要点。技术设计（架构模式、算法技巧）和产品设计（功能拆分方式、交互流程、配置化与可运营设计、权限模型）都可以收录；目标是"产品与方案参考"时以产品设计为主。

## 常见误判清单

写首屏结论、交付建议、功能归属时，下面 8 类最容易"证据只够一半，结论写满"。左列的证据**不够**下结论，至少再看右列：

| 结论 | 不够的证据 | 至少再看 |
|---|---|---|
| 某服务是可选的 | README 提到"可选"、compose 里是单独一个服务 | 配置 schema 里该项是否有默认值或标为可选；启动和初始化时是否强制调用。"可以复用已有服务"不等于"可以不要" |
| 社区版能用 | 菜单、语言包、枚举、权限开关里有它 | 界面调用的接口 → 本地实现，还是转发给商业版服务；运行时有没有授权检查。只有入口没有实现的，写"社区版有入口，实现依赖商业版" |
| 包已发布 / 没发布 | `publishConfig`、`private`、`workspace:*` | registry 上该包名和版本的记录；查不了就写"有发布配置，是否已发布未确认" |
| 模块抽不出来 | 代码量大、外部引用多 | 区分原样拿走 / 加适配层 / 重构抽取 / 只借鉴；引用多说明成本高，不说明不可行 |
| 功能稳定 | 代码存在、没有 beta 标记 | 官方定位、发布说明、测试或运行证据；同时写明本次是否验证过 |
| 依赖没有协议风险 | 部分包的 registry 协议字段 | 扫描口径（R 层第 2 条）：锁定版本、未知和失败项、包内 LICENSE、镜像组件、实际分发方式 |
| 升级无痛 | 不改源码、只包装调用接口 | 接口、数据结构、模型、迁移脚本是否兼容；列出升级时要回归的具体接口 |
| 具备某项企业能力 | 配置里有一个开关字段 | 实际的后端实现、身份映射、功能范围，以及是否需要单独采购；没有实现代码就写待确认 |

**否定和全称结论**同样容易写过头。写之前至少按右列查一遍，写的时候用"在 X 范围、用 Y 方法没找到 Z"的形式：

| 想写的结论 | 写之前至少查 |
|---|---|
| 没有配置文件 / 全部来自环境变量 | 读文件、解析配置的调用（`readFile`、`parse`、`load`、`config`）；环境变量是不是指向一个配置文件 |
| 全部由同一套机制管理（如"所有引擎都受进程监管"） | 有没有挂接已有程序、连接外部服务的分支（`attach`、`connect`、`endpoint`）；控制权是否不同 |
| 只能靠重启释放 / 内存只增不减 / 缓存或注册表只进不出 | 清理和关闭路径（`clear`、`reset`、`close`、`dispose`、`evict`、`pop`、`del`）以及谁调用它们 |
| 没有队列 | 区分独立的消息服务和进程内排队（`Queue`、`FIFO`、`pending`）；只能说"没有依赖独立的消息服务" |
| 生产代码里没有某个值或用法 | 跨所有源码目录检索（排除测试和样例），再追到实际调用点；一个反例就推翻结论 |
| 某生成物没有经过 CI 校验 | 顺着间接调用找：workflow → npm / make 脚本 → 构建工具任务 → `--check` 或 `git diff --exit-code` |
| 没有测试 / 核心路径无回归保护 | `repo_stats.py` 的测试和 CI 部分：测试代码和测试素材分开数；CI 里有没有跑测试，有没有调用其他仓库的 workflow 或检出独立的测试仓库。本仓测试少只能写"本仓就地测试较少"，覆盖度没查就写"未核实" |
| X 是唯一判据 / 只由 X 决定走哪条路 | 读完整的分支代码，把参与判断的字段和条件全部列出来；一个字段参与判断不等于它是唯一的判断依据 |
| 失败一律返回 X / 某类请求一律走 Y | 每个出错位置的处理（`except`、`catch`、`raise`、早退的 `return`）分别是什么；请求进入各条路径的全部条件。同一章的失败表、分支表要和这句话一致 |

关键词检索只是线索，命中和没命中都要追到定义和调用。查到反例时，把结论改成有范围的说法，并在 `index.md` 的「关键结论核对表」里记下这个反例。

只对首屏结论和交付决策做这一步，普通描述不必逐句对照。`checklinks.py` 会把各文档里的全称和绝对化说法列进 `_全称句清单.txt`，分强、弱两档：强档（一律、唯一、只能、从不、无回归、必然、确保等）交付前逐条对照同一章的正文、表格和待确认清单，有矛盾的改掉；弱档（只有、完全、所有等）扫一眼即可。
